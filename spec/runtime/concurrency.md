# 並行処理

`async` / `await` は**持たない**。

## 原則：関数に色を付けない

すべての関数は、上から順に実行される。
「待つ関数」と「待たない関数」を型や修飾子で区別しない。

```shark
func fetch(host: string) -> Result<string> {
  var c = try net.connect(host, 80);      // ここで待つ
  _ = try c.write_text("GET / HTTP/1.0\r\n\r\n");
  var body = try c.read_line();           // ここでも待つ
  c.close();
  return body;                            // 上から順に読める
}
```

この関数は、そのまま呼んでもよいし、タスクとして走らせてもよい。
**呼び方を変えるために関数を書き直す必要はない。**

`async` を持つ言語では、待つ関数を呼ぶ関数もまた `async` になり、
それを呼ぶ関数も `async` になっていく（関数の「色」が伝染する）。
Shark はこれを避ける。

## 同時に走らせる道具

| 道具 | 使いどころ |
|---|---|
| `task` | 関数を別のタスクで走らせる |
| `parallel` | 複数のタスクをまとめて走らせ、全部の完了を待つ |
| `channel<T>` | タスクの間で値を受け渡す |

### task

関数呼び出しの前に `task` と書くと、別のタスクとして走り始め、その場ですぐ次の行に進む。

```shark
var t = task fetch(url);     // 走り始める。ここで待たない

do_other_work();             // 別のことができる

var r = t.wait();            // 終わるまで待って結果を受け取る
```

`Task<T>` に対してできること。

| メソッド | 説明 |
|---|---|
| `wait()` | 終わるまで待ち、戻り値を受け取る |
| `done()` | 終わっていれば `true`（待たない） |
| `cancel()` | 取り消しを要求する |

### parallel

まとめて走らせて、全部終わるのを待つ。

```shark
var pages = parallel {
  task fetch(url_a);
  task fetch(url_b);
  task fetch(url_c);
};                              // ここで3つとも終わる

print(pages.len());             // 3。書いた順に並ぶ
```

`parallel` ブロックを抜けるときには、中で始めたタスクは必ず全部終わっている。
待ち忘れたタスクが裏で走り続けることがない。

ブロックの中のタスクは全て同じ型を返さなければならない。
結果は `list<T>` になる。

### channel

タスクの間で値を渡す。値は**コピーされて**渡る。

```shark
var ch = channel<int>();

task producer(ch);              // ch もコピーされるが、中身の待ち行列は共有される

var v = ch.recv();              // 届くまで待つ
ch.send(1);                     // 受け取り手がいるまで待つ
ch.close();
```

### 多対一にする

**送り手は何個でもよく、受け手は1つ**。これがチャネルの使い方の基本形。

```shark
var ch = channel<string>();

task worker(ch, "a");     // 3つのタスクが
task worker(ch, "b");     // 同じチャネルに
task worker(ch, "c");     // 送る

for var i in range(3) {
  print(ch.recv()!);      // 受け取るのはこのタスクだけ
}
```

「どれか先に終わった方を処理する」は、これで書ける。
複数のチャネルを同時に待つ必要がない。

### 種類が違うものは分ける

1本のチャネルに、意味の違う通知を混ぜない。混ぜたくなったら**チャネルを増やし、
受け取るタスクも分ける**。

```shark
var results = channel<Result<string>>();   // 取ってきた中身
var logs = channel<string>();              // 進み具合の知らせ

task collect(results);
task show_progress(logs);                  // 受け手を分ける
```

こうすると、1つのタスクが2本のチャネルを待つ場面が出てこない。

### select を持たない

複数のチャネルを同時に待つ構文（`select` にあたるもの）は**持たない**。
上の2つの決めごとで、待ちの重なりは書けるため。文法も増えない。

| やりたいこと | 書き方 |
|---|---|
| どれか先に終わった方を処理する | 送り手を増やし、受け手は1つ（多対一） |
| 種類の違う通知を捌く | チャネルと受け手のタスクを分ける |
| 種類が違うが順番を守りたい | 共通の親クラスを作り、`channel<Event>` にまとめる |
| 待っている途中でやめたい | チャネルではなく取り消しで見る（下） |

`channel` はハンドル型で、コピーしても同じ待ち行列を指す。
タスク間で共有できるのはハンドル型だけで、それ以外の値は必ずコピーされる
（[memory.md](memory.md)）。操作の一覧は
[../library/task.md](../library/task.md)。

## 待つとどうなるか

タスクが待つ関数（`sleep`、ファイル読み、通信）を呼ぶと、
**そのタスクだけが止まり、他のタスクが動く**。

```shark
sleep(1.0);     // このタスクは1秒止まる。他のタスクは動き続ける
```

「1秒待つ」を書くのに特別な記法は要らない。思想の
「OS 支援を要する関数を簡単に実現できるようにする」はここで満たされる。

## 実行のしかた

- タスクの切り替えは**仮想マシンの中**で行う。タスクごとに自前のスタックを持ち、
  待ちが発生した時点で次のタスクに切り替える
- そのため **OS のスレッドは必須ではない**。スレッドの無い環境でも並行処理が動く
  （[platform.md](platform.md)）
- **既定はスレッド1本**。すべてのタスクを1本の上で切り替える。
  複数のスレッドに割り振るかどうかは、後から決められる余地として残す
- 切り替わるのは「待ちが発生した時点」だけ。処理の途中で勝手に割り込まれることはない

スレッド1本に絞ることで、次が要らなくなる。

- ロックと排他制御
- スレッドの数を決める設定
- 「どのスレッドで動いているか」を意識した書き分け

待ちの多い処理（通信、ファイル、`sleep`）はこれで十分に重ならせられる。
CPU を使い切る計算を並列化したいときは、後から複数スレッドを足す。

## 競合が起きない理由

タスクに渡る値はコピーであり、`ref` はタスクの境界を越えられない。
そのため2つのタスクが同じデータを同時に書き換えることが起こらない。
ロックを書く必要がない（[memory.md](memory.md)）。

```shark
var xs = [1, 2, 3];
task modify(xs);       // xs のコピーが渡る。元の xs は誰も触らない
task modify(ref xs);   // エラー: ref はタスクに渡せない
```

## 取り消し

`t.cancel()` は**要求を立てるだけ**。外から待ちを断ち切らない。

- 待つ関数（`sleep`、`recv`、通信）は、待っている間ずっと要求を見ている
- 要求が立っていたら、その場で待つのをやめ、タスクを終わらせる
- 確認するのは、コアが実行を区切って戻るたび。つまり `step()` 1回ごと
  （[embedding.md](embedding.md)）。ゲームなら1フレームごと
- 取り消しが効くまでの遅れは、最大で `step()` 1回分

```shark
var t = task download(url);

if user_pressed_stop {
  t.cancel();              // すぐには止まらない。要求が立つだけ
}

var r = t.wait_timeout(time.seconds(1.0));   // 止まったかを見る
```

OS のシグナルも、待ちを叩き起こす仕組みも使わない。移植層に足すものが無い。

### 待ちの中で止まらないこと

この方法が成り立つには、**移植層が待ちっぱなしにならない**必要がある。
そのため通信の口には、次のどちらかを求める（[platform.md](platform.md)）。

- 待たずに「いま読める分」を返す形（ノンブロッキング）
- 短い制限時間を渡せる形（`step()` の刻みより短いこと）

OS の「届くまで戻ってこない」呼び出しをそのまま使うと、
そこでゲームごと止まる。コアはこれを使わない。

## panic の扱い

タスクの中で `panic` が起きたときは、そのタスクだけを止めて記録を残す。
プログラム全体は落とさない。
`wait()` で受け取ろうとしたときに、panic した旨がエラーとして返る。

## 決めていること・いないこと

並行処理まわりは、ひととおり決まった。

| 論点 | 結論 |
|---|---|
| 複数のチャネルを同時に待つ | 持たない。多対一にするか、チャネルと受け手を分ける |
| 取り消しの届き方 | 要求を立てるだけ。待つ関数が `step()` ごとに見る |
| スレッド数 | 既定は1本 |
