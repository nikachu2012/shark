# 組み込み

実行系（コア）と、それを呼ぶ側（ホスト）の境界を定める。

ホストは、学習用ゲームの本体か、`shark` コマンド（[../frontend.md](../frontend.md)）。
どちらも同じコアを呼ぶ。

ここに書く呼び出しの形は、**雛形が用意しているもの**（[../skeleton.md](../skeleton.md)）。
名前も引数も、使う側が自分のゲームに合わせて書き換えてよい。
変えてはいけないのは、下の「コアがしないこと」と、言語そのものの規則。

## コアがしないこと

コアは**単体で動くアプリではない**。次を自分からしない。

| しないこと | 代わりに |
|---|---|
| ファイルを開く | ソースは**文字列**で渡してもらう |
| 標準出力に書く | `print` の出力はホストに渡す |
| 端末にエラーを整形して出す | 診断は**構造化データ**で返す |
| コマンド引数を読む | ホストが決めて渡す |
| 勝手に時間を使い切る | 実行できる量をホストが区切る |
| 勝手にメモリを使い切る | 使ってよい量をホストが決める |

こうしておくと、画面もファイルも無いゲーム機の上で、ゲームの一部として動かせる。

## 使う流れ

```
1. 処理系を作る            create(memory_limit)   // 動かすときのメモリの上限
2. ホストの関数を登録する    register(...)
3. ソースを読み込む          load(name, source)  → 診断
4. 少しずつ動かす            step(budget)        → 状態
5. 片付ける                 destroy()
```

## ソースを渡す

```
load(name: string, source: string) -> list<Diagnostic>
```

- `name` はエラー表示に使う名前。ファイル名でなくてよい（`"ステージ3"` など）
- 型検査までを行い、見つかった誤りを全部返す。1つも無ければ実行できる状態になる
- `import` は、ホストがあらかじめ登録したモジュールの中からしか解決しない
  （[module.md](module.md)）

## 少しずつ動かす

```
step(budget: int) -> Status
```

ホストは「今回はこれだけ進めてよい」という量を渡す。
コアはその範囲まで実行して、いったん戻る。

`budget` の単位は**実行する命令の数**。経過時間ではない。
時間で区切ると、機種や負荷によって進む量が変わり、
「同じプログラムはどこでも同じ結果」という決めごと
（[platform.md](platform.md)）が崩れるため。

ホストは「1フレームあたり何命令まで」を決めて渡す。
その数を変えても、進む速さが変わるだけで結果は変わらない。

- `Status` は `running` `finished` `error` のどれか
- ゲームは毎フレーム `step()` を呼ぶ。1フレーム分だけ進み、描画に戻れる
- **無限ループを書いても、ゲームは固まらない**。`running` のまま返るだけ
- 途中で止めたいときは `abort()`。次の刻みで実行をやめる

タスクの切り替えもこの中で行う（[concurrency.md](concurrency.md)）。
待ちの発生したタスクは順番を譲り、他のタスクが同じ `step()` の中で進む。

## 使ってよいメモリの量を決める

```
create(memory_limit: int)   // 動かすときに使ってよい量（バイト）。0 なら上限なし
memory_used() -> int        // いま動いているプログラムが使っている量
```

ホストは「このステージのプログラムは何 MB まで」を決めて渡す。
プレイヤーが増え続ける配列や文字列を書いても、その量で止まる
（[memory.md](memory.md)）。

- 見るのは**実行中に使う量**。`load()` が作る構文木やバイトコードは数えない
- 超えたときは `step()` が `error` を返す。**ゲームごと落ちることはない**
- タスクの中で超えたときは、そのタスクだけが止まる（[concurrency.md](concurrency.md)）
- 上限は処理系を作るときに決める。実行の途中で変えることは考えない
- `memory_used()` は画面に出してもよい。学習用ゲームでは、
  どれだけ使っているかが見えると直し方に気づきやすい

呼び出しの深さと、タスクごとの値の置き場の大きさも、同じように作るときに決める
（[execution.md](execution.md)）。

`budget` と同じ考え方で、**動かすのに使ってよい時間もメモリも深さも、ホストが決める**。

## ホストの関数を登録する

学習用ゲームは、ゲーム側の操作を言語から呼べるようにする。
雛形では、`host` にある**関数の表に書き足す**（[../skeleton.md](../skeleton.md)）。

```
register("move", func(dir: string) -> void { ... })
```

- 登録した関数は、ふつうの関数と同じように呼べる。型も同じように検査される
- 引数と戻り値に使えるのは、基本型とコレクションだけ
- ホストの関数の中でゲームを1歩進めたいときは、`running` を返して `step()` を抜ける

```shark
// プレイヤーが書くコード
for var i in range(4) {
  move("forward");
  turn("right");
}
```

## 出力と入力を受け取る

| 受け口 | 内容 |
|---|---|
| 出力 | `print` `write` の文字列。ホストが画面のどこに出すかを決める |
| 入力 | `input()` に返す文字列。ゲームなら入力ダイアログの結果 |
| 診断 | `load()` の戻り値と、実行時の `panic` |

### まだ入力が無いとき

端末なら `read` の中で待てばよいが、ブラウザやゲームは**止まって待てない**。
そこで、行が来ているかをホストに尋ねる口を1つ置く。

| ホストが決めること | どうなるか |
|---|---|
| 尋ねる口を出さない | `input()` はその場で読む（端末のように、ホストが中で待つ） |
| 「まだ来ていない」と答える | `input()` は**待ちに入り**、`step()` はホストに返る |
| 「終端だ」と答える | `input()` は `none` になる |

待っている間も `step()` はふつうに返るので、画面は止まらない。
待ちに入ったかどうかはホストから見えるので、そこで入力欄を出したり、
刻みを休めたりできる。他のタスクは動いたまま。

```
input() を呼ぶ → 行がある   → その行を返す
              → まだ無い   → 待ち（次の刻みでまた呼ばれる）
              → 終端       → none
```

## 診断は構造化データで返す

整形はホストの仕事。端末に色付きで出すのも、ゲームの画面に吹き出しで出すのも、
同じデータから作る（[diagnostics.md](diagnostics.md)）。

```
Diagnostic {
  severity  // error / warning
  code      // "E0102"
  message   // "int と float は足せません"
  spans     // 行・桁・長さ・そこに付ける短い説明
  help      // 直し方。複数のこともある
}
```

ゲームは `message` と `help` だけを大きく出し、`code` は隠してもよい。

## 標準ライブラリの持ち込み

必須の3つ（`time` `math` `task`）以外は、ホストが**入れるかどうかを選ぶ**
（[../library/overview.md](../library/overview.md)）。
入れなかったモジュールを `import` したソースは、`load()` の時点で診断が返る。

学習用ゲームでは、段階に応じて使えるモジュールを絞れる。

## 決めていないこと

- ホストの関数にクラスを渡せるようにするか（いまは基本型とコレクションだけ）
- 途中まで動かした状態を保存して、後から続けられるようにするか
